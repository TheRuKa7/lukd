# Requirements traceability

Updated **8 November 2026 IST**. This is the current extracted technical baseline, not a statement that all game features have been implemented. Source GDD/system/UX/technical requirements are linked to an owning ADR and a named verification gate. The machine-readable [registry](tr-registry.json) retains stable IDs; append IDs rather than renumbering them. The [architecture overview](architecture.md) records open decisions.

**All registered requirements are specified; Unity implementation is not started.** “Mapped” means an ADR owns an architectural contract. “Gated” means future content remains disabled pending its own exact data and evidence. Existing reference files identify relevant test artifacts, not a claim that they cover every clause or port to Unity. There are no production story files yet; the historical [backlog](../refinement/BACKLOG.csv) identifies implementation work without implying completion.

The baseline covers the concrete technical contracts in TECH_DESIGN, SYSTEMS, GDD and their domain expansions (UX, accessibility, progression, localization, art/manga, QA and provenance). Story beats and visual descriptions that require no new system are represented by their owning content/presentation contract rather than manufactured extra subsystems. It is an extraction baseline requiring maintenance as new requirements are adopted, not an automatic proof of complete semantic coverage.

## Remaining proof and change policy

The first unresolved gate is the empty local and hosted Unity Web build, followed by a ported pure Core and typed importer. Unity save/replay/UI/accessibility/audio/performance and complete story flow remain open. Statistical balance/playtesting remains distinct from exact rule checks. Candidate ability/charms and per-locale records remain incomplete behind their individual gates. Architecture has **concerns** until engine viability and the first end-to-end Audit are demonstrated.

`python tools/check_docs.py` verifies each registry source/heading, unique ID, ADR back-reference and existing verification path. The validator deliberately rejects a newly asserted Unity implementation status under this no-Unity baseline; revise the registry and evidence contract together when a real project is added. Required future proof is a named gate and descriptive criterion, never a fabricated file link. Final asset/PDF counts are recorded in actual generation evidence and [DOC_AUDIT](../DOC_AUDIT.md).
